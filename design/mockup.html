Redis 기반 분산 락과 Redlock 알고리즘

30 Aug 2026 · redis, go, distributed-systems

여러 프로세스가 하나의 자원을 동시에 수정할 때, 우리는 상호 배제를 필요로 한다. 단일 프로세스라면 뮤텍스로 끝날 문제지만, 프로세스가 여러 노드에 흩어져 있다면 이야기가 달라진다. SET NX PX 한 줄로 시작해서, 왜 그것만으로는 부족한지까지 살펴본다.

가장 단순한 구현

Redis의 SET key value NX PX ttl은 원자적이다. 키가 없을 때만 값을 쓰고, 동시에 만료 시간을 건다. 이 두 연산이 원자적이라는 점이 핵심이다.

// Lock은 SET NX PX로 분산 락을 획득한다. 해제용 토큰을 반환한다.
func (l *Locker) Lock(ctx context.Context, key string, ttl time.Duration) (string, error) {
    token := uuid.NewString()
    ok, err := l.rdb.SetNX(ctx, key, token, ttl).Result()
    if err != nil {
        return "", fmt.Errorf("acquire lock %q: %w", key, err)
    }
    if !ok {
        return "", ErrNotAcquired
    }
    return token, nil
}

해제할 때가 더 까다롭다. DEL을 그냥 호출하면, 이미 만료된 뒤 다른 클라이언트가 잡은 락을 지워버릴 수 있다. 토큰을 비교한 뒤 지워야 하고, 그 비교와 삭제는 원자적이어야 한다.

TTL은 락의 안전장치이자 동시에 정확성의 구멍이다. 작업이 TTL보다 오래 걸리는 순간, 두 클라이언트가 같은 락을 들고 있다고 믿게 된다.

왜 Lua가 필요한가

Redis는 Lua 스크립트를 원자적으로 실행한다. GET과 DEL 사이에 다른 명령이 끼어들 수 없다는 뜻이다.

if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end

Redlock은 무엇을 더 주는가

단일 Redis 인스턴스는 그 자체가 단일 장애점이다. Redlock은 독립적인 N개 노드에 락을 걸고, 과반이 성공하면 획득으로 간주한다.

  • N개 노드 중 (N/2)+1 이상에서 성공해야 한다
  • 획득에 쓴 시간이 TTL보다 짧아야 유효하다
  • 실패하면 획득한 노드 전부에서 즉시 해제한다

설정은 다음과 같이 둔다.

[redlock]
  nodes       = ["10.0.1.11:6379", "10.0.1.12:6379", "10.0.1.13:6379"]
  ttl         = "10s"
  retry_delay = "200ms"

비교

방식안전성지연운영 비용
단일 Redis + SET NX낮음가장 낮음낮음
Redlock (N=5)중간중간높음
etcd / ZooKeeper높음높음중간

결론부터 말하면, 정확성이 돈과 직결되는 작업에는 Redis 락을 쓰지 않는 편이 낫다. 자세한 논의는 Martin Kleppmann의 글과 그에 대한 antirez의 반박을 함께 읽어보길 권한다.
